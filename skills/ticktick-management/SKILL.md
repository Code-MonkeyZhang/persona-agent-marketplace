# 滴答清单管理规范 (TickTick Management SOP)

本规范面向官方 dida365 MCP 提供的任务类工具。调用一律走 MCP 工具，不要用 curl 等方式直接请求滴答 API，MCP 客户端会自动附带授权。

## 1. 任务创建原则 (Task Creation)

### 1.1 默认位置
- **规则**：所有新任务**默认创建在"收集箱"**。收集箱是虚拟清单，`list_projects` 不带分页参数时结果里会包含它。
- **例外**：只有当用户**明确指定**要把任务放入某个特定清单时，才设置 `task.projectId`。清单 id 一律先用 `list_projects` 查询确认，不要凭清单名字猜 id。
- **操作**：调用 `create_task` 时省略 `task.projectId` 即落入收集箱。不要自作主张新建 Project。

### 1.2 时间与日期格式
- **规则**：`task.startDate` 与 `task.dueDate` 必须使用**带时区信息的 ISO 8601 格式**，同时把 `client_timezone` 参数设为用户时区。
- **用户所在时区**：默认为 `Asia/Shanghai` (UTC+8)。
- **格式示例**：
  - **正确**: `2026-10-01T09:00:00+08:00` (明确指定了 +08:00)
  - **正确**: `2026-10-01T01:00:00.000+0000` (UTC 时间)
  - **错误**: `2026-10-01 09:00:00` (无时区，容易导致时间偏移)
- **全天任务**：用户未指定具体时刻（如"明天提醒我"）时设置 `isAllDay: true`，起止时间只给日期边界。
- **提醒**：需要提醒时设置 `task.reminders`，取值格式如 `TRIGGER:-PT60M` 表示提前 60 分钟，`TRIGGER:PT0S` 表示准时。

### 1.3 批量操作
- **规则**：当用户一次性列出多个事项时，**必须使用 `batch_add_tasks`** 传入 `tasks` 数组，严禁循环调用 `create_task`。
- **注意**：`batch_add_tasks` 要求每个任务都带 `projectId`，收集箱的 id 先用 `list_projects` 查出来再填。
- **更新**：批量修改用 `batch_update_tasks`。清空某个日期字段要把 `startDate` 或 `dueDate` 设为 `1970-01-01T00:00:00.000+0000`，不是传 null。

## 2. 任务查询与汇报
- **每日汇报**：使用 `list_undone_tasks_by_date`，`search.startDate` 与 `search.endDate` 覆盖今天。该工具最大查询范围 14 天，要看逾期任务时把 `startDate` 往前拉到覆盖最早的截止日期。
- **条件筛选**：按优先级、标签、状态筛选用 `filter_tasks`。按关键词查找用 `search_task`，它只返回任务 id、标题和链接，需要完整信息再用 `get_task_by_id`。
- **展示**：向用户展示任务时，清晰列出任务标题、截止时间（转换为用户本地易读格式，如 "14:00"）和优先级。优先级取值为 0 无、1 低、3 中、5 高。

## 3. 完成与状态变更
- **完成任务**：`complete_task` 需要同时传 `project_id` 与 `task_id`，两个 id 都来自查询结果，不要手工构造。
- **放弃或重开**：`update_task` 把 `task.status` 设为 `-1` 表示放弃，设为 `0` 表示重新激活。

## 4. 错误处理
- **清单不存在**：如果用户指定的清单在 `list_projects` 结果里找不到，**不要自动创建**。应先询问用户："找不到该清单，是否创建新清单，还是放入收集箱？"
- **时间模糊**：如果用户说"晚上提醒我"，默认理解为 **19:00** 或 **20:00**，并在回复中告知用户已设定的具体时间。
- **授权报错**：调用返回 Authentication required 或 invalid_token 时，含义是本次请求没有携带授权信息，应改用 MCP 工具让客户端自动附带 token，不要据此断定授权失效或要求用户重新 OAuth。
